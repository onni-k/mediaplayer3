Build 0007 - toteutusmuistiinpanot
===================================

Lahtokohta
----------

Build 0006 oli kayttajan vahvistuksen mukaan valmis (nelja
laitetestikierrosta, "täyttää build_0006 tason"). Build 0007
rakennettiin sen paalle kayttajan toimittaman docs-paketin
(BUILD_0007_PLAN.md + viisi uutta spek-dokumenttia) ja
pyradios-referenssiprojektin mukaisesti. Aihe: soittolistat +
internetradio (RadioBrowser-API, https://api.radio-browser.info/).

TARKEA POIKKEAMA aiempaan kaytantoon: tallakertaa kayttaja toimitti
MYOS VALMIIKSI PAIVITETYT versiot ARCHITECTURE.md:sta ja
PROJECT_STRUCTURE.md:sta (otettu sellaisenaan kayttoon uutena
pohjana), MUTTA CHANGELOG.md ja HISTORY.md olivat selvasti
SUUNNITTELUVAIHEEN PLACEHOLDER-dokumentteja ("Status: Planning
completed. Implementation not yet started.") jotka eivat sisaltaneet
mitaan build 0001-0006:n yksityiskohtaista historiaa jota olen
kerannyt useiden buildien ajan (mm. kaikki oikean laitteen
loydokset/korjaukset). PAATIN SAILYTTAA omat yksityiskohtaiset
CHANGELOG.md/HISTORY.md-versiot ja lisata niihin Build 0007 -osiot
SAMASSA formaatissa kuin aiemmin, sen sijaan etta olisin korvannut ne
kayttajan suunnitteludokumenteilla -- tama sailyttaa arvokkaan,
vaivalla kerätyn historiatiedon. Uudet spek-dokumentit
(STORAGE_MANAGER_SPEC.md, PLAYLIST_MANAGER_SPEC.md,
INTERNETRADIO_MANAGER_SPEC.md, PLAYLISTSCREEN_SPEC.md,
RADIOBROWSER_SCREEN_SPEC.md) otettiin sellaisenaan kayttoon
pohjaksi, Status-kentat paivitetty vastaamaan toteutunutta tilaa.

TEKNINEN KESKEYTYS kesken session: tyokalut (bash_tool, view jne.)
lakkasivat vastaamasta kokonaan usean viestin ajaksi (todennakoisesti
infrastruktuurin ohimenevä hairio) -- tama on kirjattu rehellisesti,
tyo jatkui heti kun tyokalut palautuivat, mitaan ei menetetty koska
tiedostot pysyivat levylla koko ajan.

------------------

      (playlists/radio/artwork/cache/logs/imports/exports/backups/

      hataratkaisu /tmp (ei-pysyva, varoitus lokiin jos jouduttiin

      ajon, getXxxPath()-kutsu luo sen uudelleen automaattisesti.
    - Testattu: perus toiminta + poistetun hakemiston automaattinen
      palautuminen.

### 2. PlaylistManager (playlist_manager.py, UUSI)

    - Taysi Extended M3U -soittolistanhallinta: create/delete/rename/

### 3. InternetRadioManager (internetradio_manager.py, UUSI)

    - RadioBrowser-API-kommunikaatio Pythonin OMALLA urllib-
      kirjastolla (ei ulkoista riippuvuutta -- ei voida olettaa etta
      "requests" on asennettu vastaanottimeen).
    - Tarkistin pyradios-referenssiprojektin lahdekoodin (radios.py,
      base_url.py) kayttajan pyynnosta ennen toteutusta:
        * json/stations/search -- pahaku (name/country/language/tag)
        * json/countries, json/languages, json/tags -- suodatinlistat
        * json/url/<uuid> -- TARKEA "click counter" -konventio:
          RALIS-tason toistoa varten PITAA kutsua tata endpointtia
          ENNEN soittoa, koska se seka rekisteroi kuuntelukerran etta
          palauttaa OIKEAN, uudelleenohjaukset seuraavan
          stream-URL:n ("url_resolved") -- raakaa "url"-kenttaa ei
          pidä kayttaa suoraan. Toteutettu tasmalleen tallä tavalla
          prepareStream()-metodissa.
        * tag-parametrit ovat pienaakkosherkkia (havaittu
          pyradios-koodista) -- normalisoitu automaattisesti.
    - EI KAYTETTY pyradios:n omaa DNS-pohjaista peilipalvelin-
      loytoa (reverse-DNS-temppu) -- kayttaja pyysi kayttamaan
      suoraan "https://api.radio-browser.info/" -osoitetta, joka jo

    - Suosikkilistat (useita nimettyja listoja), historia (koko
      rajattu asetuksesta), molemmat JSON-tiedostoina

    - JOKAINEN RadioBrowser-pyynto on puolustavasti kaaritty --
      verkkovirhe/aikakatkaisu/JSON-jasennysvirhe palauttaa aina
      tyhjan tuloksen ("ei loytynyt"), EI KOSKAAN kaadu.

    verkkoyhteytta ollenkaan, joten itse RadioBrowser-API-kutsuja EI

Laitetestin kierros 1 (2026-07-23, test1.log + Build_0007_test1.zip)
------------------------------------------------------------------------

Kayttajan palaute: "Internetradio-ikkuna aukeaa, mutta ei näytä
mitään kanavia. Ilmeisesti haku ei toiminut. Soittolista toimi
oikein ainakin hakemistojen osalta." Liitteena RadioBrowser-API:n
oma dokumentaatio (HTML) ja kayttajan oma testiskripti
(serverlist_python3.py).

Loki paljasti tarkan syyn valittomasti:

    [Radio] RadioBrowser request failed: HTTP Error 404: Not Found

JOKA ikinen pyynto osoitteeseen "https://api.radio-browser.info/..."
palautti 404:n -- verkkoyhteys siis TOIMI (ei aikakatkaisua/DNS-
virhetta), mutta itse osoite oli VAARA.

Kayttajan liittama serverlist_python3.py-skripti (ja RadioBrowserin
oma API-dokumentaatio) paljasti etta olin TEHNYT VAARAN OLETUKSEN
aiemmassa build_0007-session round-1:ssa: luulin etta pelkka
"api.radio-browser.info"-domain round-robinnaa automaattisesti
peilipalvelimien valilla DNS:n kautta. TAMA ON VAARIN -- todellinen
API vaatii KAKSIVAIHEISEN mekanismin:

    1. DNS-kysely "all.api.radio-browser.info" -> lista IP-osoitteita
    2. KAANTEINEN DNS-haku (reverse lookup) jokaiselle IP:lle ->
       oikeat peilipalvelin-hostnimet (esim. "de1.api.radio-
       browser.info")
    3. Kutsu YHTA NAISTA peileista, ei koskaan suoraan
       "api.radio-browser.info":a.

Tama tasmaa TAYSIN kayttajan oman testiskriptin
(get_radiobrowser_base_urls()) ja jo aiemmin session 1:ssa lukemani
pyradios-referenssiprojektin (base_url.py) kanssa -- MOLEMMAT
kayttavat tasmalleen tata mekanismia. Aiemmin PAATIN TIETOISESTI
OHITTAA taman mekanismin kayttajan alkuperaisen ohjeen "kaytä
osoitetta https://api.radio-browser.info/" perusteella, olettaen
etta plain-domain riittaisi -- tama oletus oli VAARIN, nyt vahvistettu
oikealla laitteella.

Korjaus (internetradio_manager.py):

    - Lisatty _discoverServers(): socket.getaddrinfo() +
      socket.gethostbyaddr() -- tasmalleen sama logiikka kuin
      kayttajan serverlist_python3.py-skriptissa. Palauttaa
      FALLBACK_SERVER:in ("https://de1.api.radio-browser.info") jos
      DNS-loytö epaonnistuu kokonaan.
    - _getServers(): valimuistoi loytyneet palvelimet koko
      prosessin elinajaksi (ei toisteta DNS-hakua joka pyynnolla).
    - _apiGet() kirjoitettu uusiksi: kokeilee JOKAISTA loydettya
      peilia jarjestyksessa (viimeksi toiminut ensin, loput
      satunnaisessa jarjestyksessa) kunnes joku vastaa onnistuneesti
      -- tasmalleen sama retry-on-failure-logiikka kuin kayttajan
      skriptin downloadRadiobrowser()-funktiossa. Onnistunut peili
      tallennetaan listan kärkeen seuraavia pyyntoja varten.
    - getDiagnostics() paivitetty nayttamaan loydetyt peilit
      API_BASE_URL:in sijaan (joka poistettiin kokonaan).

Testaus: _discoverServers()'in fallback-kaytos (ei DNS:aa
hiekkalaatikossa) vahvistettu. LISAKSI kirjoitin erillisen testin
jossa MOCKATTIIN kolme peilipalvelinta (kaksi epaonnistuu, kolmas
onnistuu) ja vahvistettiin: (a) kaikkia kolmea kokeillaan
jarjestyksessa, (b) onnistunut peili tallennetaan listan karkeen,
(c) SEURAAVA pyynto kokeilee VAIN sita yhta peilia ensin (ei enaa
kaikkia kolmea). Koko regressiosarja + plugin.main() ajettiin
uudelleen lapi ilman virheita.

Soittolistan hakemisto-lisays ("Add Folder to Playlist") vahvistettu
toimivaksi kayttajan toimesta -- ei vaatinut korjauksia.
