## Round 1 (2026-08-08)

### Completed: the two Build 0009 exception-audit fixes

Both were fully specified already (from the audit itself, and BUILD_0010_PLAN.md
confirms the user wants them addressed), so implemented immediately rather than
deferred:

1. **BrowserScreen startup directory guard**
   (`browserscreen.py::_initialize()`): `createFileList(startup_directory)`
   had no exception guard, and its own docstring says it re-raises
   when the directory doesn't exist -- a disconnected USB drive or
   unmounted network share as the configured startup directory would
   crash BrowserScreen outright. Fixed: checks `os.path.isdir()`
   first and falls back to "/" (always exists) if unavailable; also
   wraps the actual `createFileList()` call itself defensively, in
   case the directory disappears in the brief window between the
   check and the call. Tested: constructing BrowserScreen with a
   nonexistent startup directory no longer raises, and the normal
   (existing-directory) case is unaffected.

2. **Top-level MainScreen startup protection** (`plugin.py::main()`):
   `session.open(MainScreen)` had no exception guard at all, even
   though every individual step *before* it already did -- directly
   responsible for how severe the two real Build 0009 device crashes
   turned out to be (a malformed XML skin comment, an unverified
   onLayoutFinish API), since both propagated straight to Enigma2's
   own crash handler with nothing to catch them. Fixed: wraps the
   call, logs the full traceback (`traceback.format_exc()`), and
   shows a MessageBox error dialog instead of letting the exception
   propagate uncontrolled. Tested: a simulated MainScreen construction
   failure now surfaces as a MessageBox rather than crashing
   `plugin.main()`; the normal successful-startup case is unaffected.

Full regression (`plugin.main()`) and skin XML validation (MainScreen,
BrowserScreen, SettingsScreen) both pass after these two changes.

### Blocking issue: Podcast Index authentication needs BOTH a key and a secret

Read the PodcastIndex example code (`podcasting-index.py`) carefully.
Confirmed the API's auth scheme (Amazon-S3-style):

    Authorization header = sha1(api_key + api_secret + unix_timestamp).hexdigest()
    X-Auth-Date header    = str(unix_timestamp)
    X-Auth-Key header     = api_key

This requires **both** api_key and api_secret -- the uploaded
Podcast_index_API_KEY.txt only contains an api_key
("ZBSFDTTUETXB7DJV2KTY"). Cannot complete the actual PodcastIndex
provider's authentication without the secret too. Flagged this to the
user; asked for it before proceeding further with the live API
integration.

Also raised, per the user's own request to embed the key "even if
encrypted": true security isn't achievable by bundling a shared
secret + its own decryption logic inside a publicly distributed
plugin (Build 0010 -> 1.0-beta is explicitly headed for public
testing) -- anyone who downloads it gets the decryption code too.
Proposed: light obfuscation (not plaintext) for a bundled default key
as a convenience so podcasts work out of the box, PLUS a
Settings-configurable personal key/secret (mirroring the existing Yle
EPG app_id/app_key pattern) as the actually-robust option, and noted
the shared-key approach also risks Podcast Index's own rate limits if
usage scales across many users. Not yet implemented -- waiting on the
secret before building the real auth path (no point obfuscating a
key I can't yet use).

### PodcastIndexProvider (new: podcast_providers/podcastindex/podcastindex_provider.py)

Mirrors epg_providers/Finland_radio_epg/'s own structure and
conventions closely. Implements PODCAST_PROVIDER_SPEC.md's interface:
searchPodcasts(query), getPodcast(podcast_id), getEpisodes(podcast_id),
refreshPodcast(podcast_id).

- **Auth**: confirmed Amazon-S3-style scheme from the reference
  example (podcasting-index.py) and cross-checked against three
  independent third-party implementations found via web search (all
  identical): Authorization = sha1(api_key + api_secret +
  unix_timestamp).hexdigest(), plus X-Auth-Date and X-Auth-Key
  headers. Reimplemented with urllib (stdlib) instead of the
  reference example's `requests` dependency, matching every other
  network call in this project. Verified the header computation
  matches an independently-recomputed hash exactly in testing.
- **Credentials**: `_resolveCredentials()` prefers the user's own
  Settings-provided key/secret (cfg.podcast.podcastindex_api_key/
  podcastindex_api_secret, new config entries + SettingsScreen rows)
  over a bundled default pair -- falls back to the default only when
  BOTH user fields are empty (a half-set user pair does NOT get
  mixed with the default, tested explicitly). The bundled default
  (the credentials the user supplied) is stored XOR+base64
  "obfuscated", not plaintext -- explicitly NOT real security (this
  project is headed for public 1.0-beta distribution, so the
  deobfuscation logic ships in the same file anyone can read) --
  discussed this limitation with the user before implementing;
  their own Settings key/secret is the only genuinely private path,
  and also avoids every installation sharing the bundled key's rate
  limit.
- **Error handling**: every category PODCAST_PROVIDER_SPEC.md's
  "Error Handling" section lists tested individually against a
  mocked urllib.request.urlopen: network unavailable (URLError),
  HTTP failure (HTTPError, e.g. 401/429), invalid JSON, and Podcast
  Index's own "status": "false" response-body convention (used for
  some failures even on HTTP 200, confirmed from their docs) -- all
  degrade to an empty list / None, nothing raises.
- **Data conversion**: Podcast Index's "feed"/"item" JSON shapes
  (confirmed via pypi.org's python-podcastindex package docs, which
  show real sample responses) converted to the common podcast/episode
  dicts PODCAST_PROVIDER_SPEC.md defines. getEpisodes() filters out
  episodes with no usable enclosureUrl before returning them, per
  spec ("PodcastManager shall not offer them as playable items") --
  tested explicitly.

### PodcastManager (new: podcast_manager.py)

Mirrors InternetRadioManager's own pattern (JSON persistence under
storage_manager's convention, load/save helpers that never raise).
New storage_manager.getPodcastPath() (mirroring getRadioPath()) and
"podcast" added to the ensured-subdirectories list at startup.

- Subscriptions: subscribe()/unsubscribe()/isSubscribed()/
  getSubscriptions(), persisted to subscriptions.json. Subscribing an
  already-subscribed podcast is a no-op (not a duplicate) -- tested.
- Episodes: getEpisodes() caches per podcast_id in memory after the
  first fetch, only refetches on explicit force_refresh=True or if
  nothing's cached yet -- and critically, a failed/empty refresh
  keeps the previously cached episodes rather than wiping them out
  (PODCAST_MANAGER_SPEC.md "Refresh Behaviour": "A failed refresh
  shall not remove previously stored valid information") -- tested
  explicitly with a provider that fails on the second call.
- refreshPodcast(): updates a subscription's metadata in place on
  success (preserving the original subscribed_at timestamp), leaves
  it completely untouched on failure -- both tested.
- searchPodcasts() delegates to the provider with its own outer
  try/except as defense-in-depth (mirrors EPGManager's own pattern
  around ITS provider calls), even though the provider itself never
  raises.

All of the above tested in the stub environment: credential
resolution/priority, the exact auth header hash, realistic mocked API
responses (search + episodes), every documented error category,
subscription CRUD, episode caching/refresh resilience. Full
plugin.main() regression and SettingsScreen skin XML validation both
still pass.

### Fixed: episode title corruption when adding to a playlist (+ "(Podcast)" suffix)

User requested podcast episodes added to a playlist show a
"(Podcast)" suffix, mirroring PlaylistScreen's own existing "(Radio)"
convention for its combined playlist/radio-favorites list. While
implementing this, found the underlying mechanism this exposed: without

PodcastScreen._addEpisodeToPlaylist() to pass the episode's own real
title with a "(Podcast)" suffix appended, rather than ever deriving one
from the URL. Tested: the exact corrupted-title URL from the device log
now produces a clean stored title; the local-file case (no title
argument) is provably byte-for-byte unchanged.

## Round 5 (2026-08-09) -- second device test (test_2_openvix.log)

### Fixed: podcast episodes silently unplayable once added to a playlist

Log showed the user subscribing, adding a Nikotellen episode to the
"suomi" playlist (Round 4's new "(Podcast)" title-suffix path working
correctly), then playing that playlist: "[Playlist] Playlist loaded:
suomi (1 track(s))" immediately followed by "[Playlist] Missing file
skipped: https://feeds.soundcloud.com/stream/...\" and "1 missing
file(s) skipped" -- an empty playback queue, no error shown, nothing
audible happened.

Root cause: playlist_manager.py's validatePlaylist() (used by both
generatePlaybackQueue() and browserscreen.py's own queue building)
called os.path.isfile(path) unconditionally on every track's stored
path. That was a safe assumption right up until Build 0010: local
playlists only ever contained local file paths before podcasts
existed. A podcast episode's path is an http(s):// URL --
os.path.isfile() always returns False for one, so every podcast
episode was being validated out of every playlist on every playback
attempt, unconditionally, with the existing "missing file" logging
making it look like a disappeared local file rather than what it
actually was.

Fixed: validatePlaylist() now treats any path starting with http:// or
https:// as valid without an os.path.isfile() check (existence isn't
a meaningful/checkable concept for a remote URL the way it is for a
local file -- matches playback_controller.py's own existing reasoning
for why podcast/radio URLs need no separate playback path). Local
paths still go through the original os.path.isfile() check unchanged.
Tested: the exact URL from the device log now passes validation; a
genuinely missing local file is still correctly skipped; an existing
local file still passes -- all three cases verified explicitly, plus
http:// (not just https://) covered too.

### Root cause: Python widget-insertion order, not XML declaration order

Real bug, not a rendering quirk. Enigma2's paint/z-order for same-
screen widgets follows the order components are added to `self`
in Python (`self[name] = Widget(...)`), not the order widgets are
declared in the skin XML string. PodcastScreen/BrowserScreen's own
_initialize() already (correctly, if not deliberately documented as
load-bearing before now) adds bg_normal, then bg_active, then the
title widget, per column, in that order -- title added LAST, so it
paints on top. Round 9's edits to MusicLibraryScreen/RadioBrowser
Screen/PlaylistScreen added the title widgets to `self` FIRST, then
the bg widgets afterwards in a separate loop -- exactly backwards,
so the opaque bg rectangles painted over the title text and hid it
completely. The skin XML itself was correct in all three cases
(verified again by inspection) -- only the Python insertion order was
wrong. Fixed by reordering _initialize() in all three files to match
PodcastScreen's own working order (bg widgets added before title
widgets), and documented this ordering dependency explicitly in all
three files' comments so it doesn't get silently broken again the
next time a title widget's initialization is touched.

### Local station database (BUILD_0010_PLAN.md "RadioBrowser Database" / RADIOBROWSER_SPEC.md "Local Station Database")

internetradio_manager.py previously had no persistent station storage
at all -- every search/getCountries()/getLanguages() call hit the live
RadioBrowser API directly (a vestigial, never-wired-up
_searchCachePath() was the only hint this was ever planned; removed
it as part of this round since the real thing now exists). Added:

- **Storage**: stations.json under storage_manager.getRadioPath(),
  `{"last_updated": <unix ts>, "stations": [...]}`. Capped at 20000
  stations (RADIOBROWSER_SPEC.md doesn't mandate mirroring the entire
  global catalogue -- tens of thousands of stations of little
  individual interest would cost real storage/memory on a set-top box
  for minimal benefit), downloaded ordered by RadioBrowser's own
  clickcount (popularity) rather than an arbitrary or alphabetical
  slice, documented as a deliberate trade-off in code.
- **updateStationDatabase()**: downloads, validates each entry has a
  name and a usable stream URL, writes to a `.tmp` path and
  `os.replace()`s it over the real file only after the write succeeds
  (RADIOBROWSER_SPEC.md "Database Integrity" -- atomic on the same
  filesystem, so a crash mid-write can never corrupt the existing
  database). A failed/empty/invalid response leaves the existing file
  completely untouched.
- **clearStationDatabase()**: deliberately separate from a normal
  update, which never removes stations on its own (RADIOBROWSER_SPEC.md
  "A separate 'Clear station list' operation may remove the existing
  stations").
- **search()/getCountries()/getLanguages()**: same public signatures,
  now local-database-first (in-memory filtering: substring match on
  name/tag, exact match on country/language, aggregated
  {name, stationcount} counts for countries/languages) -- falls back
  to the original live-API behaviour only when the local database has
  never been populated, so the app isn't dead on arrival before the
  first sync.
- **shouldAutoUpdateDatabase()**: config-driven (new cfg.radio.
  database_auto_update, default on; cfg.radio.database_update_
  interval_days, default 7, matching RADIOBROWSER_SPEC.md's own
  suggested default) -- answers the question only, never triggers an
  update itself; callers decide when/how to act on it.

All of the above unit-tested standalone with a mocked _apiGet() (no
real network available in this sandboxed session either): empty-state
behaviour, successful download with invalid-entry filtering, local
search (both exact and substring matching), country/language
aggregation, cross-process-instance persistence, clear, and -- the
most important case -- a failed update provably leaving a previously-
good database completely untouched. Also explicitly regression-tested
that search()/getCountries() still correctly fall back to a live API
call when the local database is genuinely empty.

plugin.py's Plugins() now conditionally appends a second
PluginDescriptor(where=PluginDescriptor.WHERE_MENU) alongside the
always-present WHERE_PLUGINMENU (Extensions menu) one, when that
config value is on. Got one real implementation detail right rather
than assumed: WHERE_MENU's own `fnc` calling convention is genuinely
different from WHERE_PLUGINMENU's -- Enigma2 calls a WHERE_MENU
plugin's fnc as `fnc(menuid, **kwargs)` for every menu it builds (not
just the main menu), and it must return a list of
(name, function, unique_id, weight) tuples (or [] to contribute

construction or silently shown nothing anywhere -- added a small
dedicated mainMenu(menuid, **kwargs) function instead, checking
`menuid == "mainmenu"` explicitly, which then calls the *same*
existing `main(session)` when the entry is actually selected (its
signature already matches what Enigma2's menu machinery calls it
with, no changes needed there).

PluginDescriptor(**) is evaluated once when Enigma2 loads its plugin
list (startup or an explicit rescan), not live -- so toggling this
Settings entry needs a GUI restart before the main menu entry
actually appears or disappears. Documented directly in the Settings
label itself ("restart required") rather than left as a surprise, and
explained in Plugins()'s own docstring.

Verified standalone (mocked PluginDescriptor, no real Enigma2 needed
for this particular logic): toggle off produces exactly one descriptor
(Extensions menu only); toggle on produces both; mainMenu("mainmenu")
correctly contributes the one expected entry; mainMenu() called for
any other menuid correctly contributes nothing.

## Round 24 (2026-08-15) -- critical startup crash fix + .ipk removal cleanup

### Startup crash: invalid XML comment in Round 23's own skin edit

test1_openvix_6_9_001.log: MainScreen failed to open at all --
`xml.etree.ElementTree.ParseError: not well-formed (invalid token):
line 59, column 58` inside readSkin(), then a second, unrelated crash
(RuntimeError: modal open not allowed) while plugin.py's own
error-reporting MessageBox tried to open from a non-modal context --
a real, separate minor gap in the error-handling path itself
(session.open() for a MessageBox at top-level main() apparently isn't
always safe to call this way), noted but not chased this round since
the actual root cause made it moot; worth a look if a startup error
MessageBox is ever needed again.

Root cause of the real crash: XML forbids "--" ANYWHERE inside a
`<!-- -->` comment body, not just adjacent to the delimiters -- Round
23's own new comments in mainscreen.py's _buildSkin() used " -- " as
a prose separator (this project's own house style throughout every
Python comment) inside three separate `<!-- -->` blocks, which is
completely fine in a Python `#` comment but invalid inside emitted
XML. This is exactly the class of bug that can't be caught by
py_compile or an AST sweep (both already run last round) -- it only
exists in the XML *content* produced by an f-string at runtime, which
requires actually rendering and parsing the skin to catch.

Fixed by replacing "--" with ":" in the three comments. Then went
further than a manual fix this time: extracted _buildSkin() as a
standalone function (via source-slicing + minimal mocked dependencies
-- skin_manager, to_opaque_skin_color, PANEL_BACKGROUND_COLOR/
PANEL_TEXT_COLOR, get_version_string, MainScreen.DESIGN_WIDTH/HEIGHT)
and ran the ACTUAL generated XML through Python's own
xml.etree.ElementTree.fromstring() -- the exact same parser Enigma2's
own readSkin() uses per the crash traceback -- at four different
resolutions (700x520, 720x576, 1280x720, 1920x1080). All parse
cleanly now. Also grepped every other screen file's own `<!-- -->`
comments (if any) for the same class of bug across the whole
codebase -- none found; this was isolated to Round 23's own new
comments in mainscreen.py, not a pre-existing or wider issue.

This is a good general lesson for this project going forward:
whenever a skin-XML f-string changes, actually rendering and
XML-parsing the result (not just py_compile/AST) is now the right
verification step, not just something to consider -- adopting this
as standard practice, not a one-off exercise, since normal
static-analysis tooling structurally cannot catch this whole class of
bug (it lives entirely in string content, not Python syntax).

### .ipk: guaranteed complete removal on uninstall, settings preserved

Direct request: opkg removal should delete the whole MediaPlayer3
install directory and everything in it, but leave the separate
settings/data directory (.mediaplayer3, under /media/hdd/ or /media/
depending on the receiver -- storage.py) alone, ready for the next
install.

opkg already only ever removes the files it itself tracked from a
package -- runtime-created files it never installed (Python's own
__pycache__/*.pyc, generated the first time each module actually
runs) are invisible to it and get left behind after every removal,
along with the now only-those-files-containing directory. Added a
postrm script (runs after opkg's own file removal, executable
permission confirmed preserved through the tar/ar packaging by
re-extracting and checking it) that does exactly one thing: `rm -rf`
the plugin's own install path. Deliberately does not reference
/media/ or the settings directory at all, anywhere in the script, so
there's no way for it to reach into the wrong place even by mistake.
